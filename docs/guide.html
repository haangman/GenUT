GenUT 사용 가이드

GenUT가 무엇으로 이루어져 있고, 어떤 순서로 테스트를 만들며, 어떻게 설치·설정해 쓰는지, 문제가 생기면 어떻게 디버깅하고 튜닝하는지를 처음 보는 사람도 따라갈 수 있게 정리했습니다.

gtest · KUnit예시는 모두 실제 실행 결과설계: docs/design.htmlKUnit 스크립트 계약: docs/kunit-script.md

이 문서의 예시는 모두 실제 실행 결과입니다. 저장소의 샘플 프로젝트(tests/fixtures/sample_project)를 복사해 genut 명령을 처음부터 끝까지 실행하고, 터미널 출력과 실행 기록 파일을 그대로 옮겼습니다. 빌드·실행·커버리지·크래시 분석은 실제 도구(MSYS2 gcc 16, CMake 4.4, GoogleTest 1.18, gdb)가 했습니다. LLM만 비용과 재현성을 위해 응답을 미리 적어 둔 가짜 provider(llm.provider = "fake")를 썼습니다. 실제 LLM을 쓰면 응답 내용은 달라지지만 흐름과 산출물의 형태는 같습니다. 긴 경로는 ~/work/sample(프로젝트), ~/.genut(GenUT 홈)처럼 줄였습니다.

1GenUT 한눈에 보기

GenUT는 C/C++ 소스 파일과 함수 이름을 주면 그 함수의 단위 테스트를 자동으로 만들어 주는 도구입니다.

대상 코드만드는 테스트빌드·실행 방법
유저 스페이스 C/C++GoogleTest(gtest)GenUT가 전용 CMake 빌드 디렉터리를 구성해 직접 빌드·실행
리눅스 커널 CKUnit사용자가 준비한 실행 스크립트(커널 빌드 + QEMU 실행)를 정해진 인자로 호출

핵심 원칙 다섯 가지

순서는 코드가, 판단은 LLM이단계 진행·빌드·실행·판정은 파이썬 코드가 하고, LLM은 "케이스를 써라", "이 실패를 어떻게 고칠까" 같은 좁은 질문에만 정해진 JSON으로 답합니다.
통과한 것만 남긴다실제로 빌드·실행되어 통과한 케이스만 최종 파일에 들어갑니다. 일부만 통과해도 통과분은 버리지 않습니다.
케이스 단위로 고친다실패한 케이스 하나만 다시 씁니다. 이미 통과한 케이스는 글자 하나 바뀌지 않습니다.
원시 로그 대신 구조화된 정보수만 줄 로그 대신 "분류 + 핵심 진단 + 크래시 위치"만 LLM에 줍니다. 원본은 실행 기록에 그대로 남깁니다.
소스 트리를 더럽히지 않는다작업은 전용 빌드 디렉터리와 ~/.genut에서 하고, 소스 트리에는 최종 테스트 파일만 씁니다.

2.4 실행 상태: 함수 → 케이스

한 번의 실행(RunState)은 소스 파일 하나를 다루고, 그 안에 함수별 상태(FunctionState), 그 안에 케이스(TestCase)가 있습니다. 진행 단위는 케이스입니다.

상태뜻
new아직 검증 전 (처음 쓰였거나 고쳐진 직후)
pass통과. 이후 본문이 바뀌지 않음
fail / crash실패. 수정 루프 대상
not_run같은 실행 파일의 앞 케이스가 죽어서 실행되지 못함. 다음 빌드에서 다시 실행
dropped제거됨 (수정 한도, Fixer의 drop_case 등). 최종 파일에 안 들어감
suspected_bug테스트가 아니라 소스가 틀렸을 가능성. 리포트와 suspected_bugs.md에 남음
flaky소스가 같은데 빌드마다 결과가 달라 제외

여러 케이스가 함께 쓰는 include·헬퍼 함수는 공유 영역으로 따로 관리합니다. 공유 영역을 바꾼 뒤 통과 케이스가 깨지면 그 변경을 되돌립니다.

3동작: 테스트가 만들어지는 8단계

3.1 단계별 상세

단계누가하는 일실패하면
① 분석코드 + Analyzerlibclang으로 시그니처·소스·분기·반환 지점·호출·타입·전역·상수를 뽑고, 호출마다 링크 범위(같은 파일 / 링크하는 타깃에 있음 / 외부 / 정의 없음)를 판정. Analyzer가 테스트 가능 여부·주의 사항·추천 케이스를 냄테스트 불가면 그 함수는 untestable
② 스텁코드정의 없는 심볼과 ## 반드시 스텁 규칙 정리. 스텁 도구 연동 전이라 지금은 스텁을 만들지 않음—
③ 사전검증코드케이스 없는 뼈대만 빌드해 환경(include, 링크, CMake)을 확인. 뼈대·환경이 이전 성공과 같으면 캐시. 빌드가 slow_build_threshold_sec(120초)보다 느리면 스모크를 생략infra_error로 실행 종료 (LLM 비용 없음)
④ 스모크Test Writer가장 단순한 정상 경로 케이스 하나로 뼈대·include·링크가 실제로 맞는지 확인수정 루프
⑤ 확장Test Writer오류 반환·경계값·NULL 케이스 추가. 모든 함수를 한 번에 빌드하고 함수별로 실행수정 루프
⑥ 수정코드 + Fixer실패를 분류하고 권장 전략을 정한 뒤 Fixer가 그 케이스만 다시 씀. 크래시면 의심 케이스만 다시 실행(격리)해 gdb 백트레이스로 크래시 브리프를 만듦한도를 넘으면 제거
⑦ 커버리지코드 + Test Writer통과 케이스만 다시 실행해 gcov로 라인 커버리지를 재고, 못 밟은 줄마다 도달 조건을 붙여 케이스를 더 받음. 라운드가 끝나도 남은 줄은 Unreachable Analyzer가 이유를 분류(unreachable_defensive, needs_stub_behavior, config_dependent, optimized_out, unknown)새 케이스는 수정 루프로
⑧ 리뷰코드 + Reviewer코드 검사(아래 3.3)는 통과 즉시, Reviewer는 마지막에 규칙의 의도·무의미한 단정·단정 약화·커버리지용 케이스의 확인 누락을 봄지적된 케이스는 한 번만 고치고, 안 되면 제거
최종 확인코드통과 케이스만 담은 파일로 다시 빌드·실행(final_build_reserve만큼 빌드를 남겨 둠). 깨지면 녹색 스냅샷으로 되돌림. 통과분을 프로덕트 트리에 설치스냅샷 사용 또는 미확인 표시
노트Note Keeper배울 것이 있는 실행이면 다음 생성에 도움이 될 노트를 남김. 범위(공통/프로덕트)는 코드가 정함실패해도 마무리는 계속

3.2 실패 분류와 전략 사다리

실패는 먼저 코드가 분류하고, 분류마다 권장 시작 전략이 있습니다. Fixer는 권장 전략과 그보다 더 포기하는 쪽(오른쪽)만 고를 수 있습니다.

fix_case케이스 고치기→ add_stub스텁 추가→ drop_case케이스 제거→ narrow_scope범위 축소→ give_up함수 포기
분류언제권장 전략
missing_include선언을 못 찾음, unknown type name, implicit declarationfix_case
undeclared_identifier없는 이름·필드를 씀fix_case
type_mismatch인자 개수·타입 불일치fix_case
warning_as_error-Werror로 경고가 오류가 됨fix_case
compile_error그 밖의 컴파일 오류fix_case
undefined_reference링크 시 정의 없음add_stub (스텁 도구가 없으면 narrow_scope)
duplicate_symbol스텁과 실제 정의 충돌add_stub
assertion_failed단정 실패fix_case
crash세그폴트, 새니타이저, 커널 oops·KASAN 등fix_case (같은 케이스가 또 죽으면 제거)
timeout시간 초과drop_case (한 번은 고쳐 봄)
review_reject코드 리뷰 검사나 Reviewer 지적fix_case
context_overflow필수 프롬프트만으로 LLM 한도 초과narrow_scope
infra_error환경 문제 (사전검증 실패, LLM 연결 실패 등)give_up — 실행을 멈춤

컴파일 오류 분류 규칙은 src/genut/verify/classify.yaml에 있어 코드 수정 없이 패턴을 추가할 수 있습니다(위에서부터 처음 맞는 규칙).

gtest 단정 실패를 읽는 법

gtest가 낸 실패 메시지는 단정 종류별로 식과 값을 뽑아 한 줄로 요약합니다. 이 요약이 터미널·리포트·수정 기록·Fixer 프롬프트의 "요약"이고, 원문 메시지는 "상세"에 그대로 남습니다. [ ] 안이 실행 중 계산된 값입니다.

EXPECT_EQ / STREQ / FLOAT_EQ같지 않음: rb_push(&rb, "abcdef", 6) [-28] ≠ RB_OK [0]한쪽에만 함수 호출이 있으면 그쪽을 실제값으로 채움 (인자 순서와 무관). 둘 다 호출이면 비움

EXPECT_THAT조건 불일치: push(6) → -28 (기대: is equal to 0)매처 설명 · 값

<< "메시지"로 붙인 설명은 — 메시지로 덧붙고, 한 케이스에 실패가 여럿이면 첫 실패를 요약하고 외 N건을 붙입니다. 기대값·실제값은 Fixer 프롬프트에 기대값: … · 실제값: …으로 들어가고, 실제값 베끼기 검사는 기대값 쪽 값을 베끼기로 보지 않습니다.

대상은 샘플 프로젝트의 링 버퍼 함수 rb_push입니다. 반환 지점이 넷(:31 EINVAL, :34 ENOSPC, :38 ENOMEM, :42 OK)이고, 다른 라이브러리(rbslot)의 rb_alloc_slot을 부릅니다.

int rb_push(struct rb *rb, const void *data, size_t len)
{
	unsigned char *slot;

	if (rb == NULL || data == NULL)
		return RB_EINVAL;              /* :31 */
	if (rb_free_space(rb) < len) {
		stats.full_count++;
		return RB_ENOSPC;              /* :34 */
	}
	slot = rb_alloc_slot(rb, len);     /* slot.c (rbslot 타깃) */
	if (slot == NULL)
		return RB_ENOMEM;              /* :38 */
	memcpy(slot, data, len);
	rb->tail += len;
	stats.push_count++;
	return RB_OK;                      /* :42 */
}
