GenUT 설계 문서

C 함수 하나를 가리키면 gtest 또는 KUnit 단위 테스트를 만들고, 직접 빌드·실행해서 통과하는 것만 남겨 주는 도구의 설계입니다.

검토 중 코드 구현은 이 문서를 함께 검토하고 합의한 뒤 시작합니다. C 코드나 테스트 도구를 잘 모르는 사람도 흐름을 이해할 수 있도록 썼고, 구현자가 그대로 따라 만들 수 있을 만큼 구체적으로 적었습니다.
1한눈에 보기

GenUT가 하는 일

GenUT는 C 함수 하나를 가리키면 그 함수를 검증하는 단위 테스트를 자동으로 만들고, 직접 빌드하고 실행해서 통과하는 것만 남겨 주는 도구입니다.

  • 유저 스페이스 C/C++ 프로젝트에는 GoogleTest(gtest) 테스트를 만듭니다.
  • 리눅스 커널 코드에는 KUnit 테스트를 만듭니다.

사람이 하는 일은 두 가지뿐입니다.

  1. "이 파일의 이 함수를 테스트해 줘"라고 지정한다.
  2. 꼭 지켜야 할 규칙을 짧은 md 파일에 적어 둔다. (예: "테스트 이름은 test_<함수명>_<상황>으로", "실제 하드웨어 레지스터는 절대 건드리지 말 것")

나머지는 GenUT 안의 여러 에이전트(각자 역할이 정해진 LLM 작업자)가 알아서 합니다. 코드를 읽고, 필요한 스텁을 만들고, 테스트를 쓰고, 빌드하고, 실행하고, 실패하면 원인을 분석해서 고치고, 그래도 안 되면 그 케이스만 버리고 나머지를 살립니다.

입력과 출력

입력출력
소스 파일 경로 (+ 선택적으로 함수 이름)함수별 테스트 파일. 최종 확인을 통과한 케이스만 담으며, 일부 케이스만 통과해도 만들어진다
compile_commands.json (빌드 플래그 정보)필요 시 스텁 파일
규칙 md (rules/)리포트: 통과한 케이스, 버린 케이스와 이유, "소스 버그 의심" 목록
빌드/실행 환경 (CMake 또는 커널 실행 스크립트)실행 기록 (모든 판단과 로그, 나중에 들여다보고 튜닝하는 용도)

genut doctor

genut gen --backend gtest --file src/ring_buffer.c --func rb_push

핵심 설계 원칙

순서는 코드가, 판단은 LLM이무엇을 언제 할지는 Python 상태 머신이 정하고, LLM은 좁은 질문에만 답한다
규칙만 사람이 쓴다사람은 rules/*.md에 꼭 지킬 것만 적고, 나머지는 에이전트가 판단한다
원시 로그는 LLM에 주지 않는다컴파일 오류, 테스트 로그, 커널 크래시는 전부 코드가 먼저 구조화·축약한다
케이스 단위로 전진한다통과한 테스트 케이스는 절대 잃지 않고, 실패한 케이스만 고치거나 버린다. 예산이 끝나거나 중단돼도 통과분으로 최종 파일을 만든다
모델은 바꿔 끼운다개발은 Claude로, 운영은 사내 Gemma 4로. 설계는 Gemma 4 수준을 기준으로 한다
모든 실행은 되돌아볼 수 있다모든 프롬프트·응답·판단·로그를 실행 기록에 남기고 HTML로 본다
측정 없이 튜닝 없음같은 코퍼스로 성공률을 재고, 규칙·프롬프트 변경의 효과를 숫자로 비교한다
공통과 프로덕트를 가른다한 번 셋업한 GenUT로 여러 프로덕트를 다룬다. 쌓이는 정보는 프로덕트 무관(공통)과 프로덕트별로 분리 저장하고 섞지 않는다
2용어집

처음 보는 용어가 있으면 여기서 찾아보세요. 이 문서에서는 아래 뜻으로만 씁니다.

용어뜻
단위 테스트함수 하나(또는 아주 작은 단위)가 의도대로 동작하는지 확인하는 작은 프로그램. "입력 X를 주면 출력 Y가 나와야 한다"를 코드로 적은 것
테스트 케이스단위 테스트 안의 한 가지 상황. 예: "빈 버퍼에 push하면 성공한다", "가득 찬 버퍼에 push하면 -ENOSPC를 돌려준다". GenUT는 케이스를 하나씩 독립적으로 다룬다
gtestGoogleTest. 유저 스페이스 C/C++용 테스트 프레임워크. TEST(Suite, Name) { EXPECT_EQ(a, b); } 형태
KUnit리눅스 커널 안에서 돌아가는 테스트 프레임워크. KUNIT_EXPECT_EQ(test, a, b) 형태. 커널을 빌드해서 실행해야 한다
스텁(stub)테스트 대상 함수가 호출하는 다른 함수를 가짜로 바꿔 끼운 것. 예: 실제 하드웨어를 읽는 read_reg() 대신 정해진 값을 돌려주는 가짜. 이 프로젝트는 gtest용, KUnit용 자체 스텁 도구를 각각 가지고 있다
compile_commands.json"이 파일을 컴파일할 때 이런 플래그를 썼다"를 파일별로 적어 둔 JSON. CMake는 옵션 하나로, 커널은 make compile_commands.json으로 만든다. 정적 분석기가 소스를 정확히 읽으려면 이게 필요하다
libclangclang 컴파일러의 분석 기능을 라이브러리로 쓰는 것. 소스를 "진짜 컴파일러가 이해하는 방식"으로 읽어 함수 시그니처, 타입, 호출 관계를 알려 준다
정적 분석코드를 실행하지 않고 읽어서 구조를 파악하는 것. GenUT는 libclang으로 한다
KTAPKUnit이 결과를 출력하는 텍스트 형식. ok 1 test_name / not ok 2 test_name 같은 줄로 되어 있다
oops / panic커널이 치명적 오류를 만났을 때 찍는 로그. 호출 스택(Call Trace), 레지스터 값 등이 길게 나온다. 사람도 읽기 어렵다
KASAN / UBSAN커널 메모리 오류(해제 후 사용, 범위 초과 등)와 정의되지 않은 동작을 잡아 주는 디버그 기능. 켜 두면 크래시 원인이 로그에 명시된다
LLM대형 언어 모델. 이 프로젝트에서는 Claude(개발용)와 Gemma 4(운영용)
에이전트특정 역할(분석, 작성, 수정 등)을 맡은 LLM 작업자. 역할마다 다른 지시문과 입력·출력 형식을 가진다
오케스트레이터에이전트들을 순서대로 부르고, 결과를 보고 다음 행동을 정하는 Python 코드. LLM이 아니다
ProviderLLM API를 감싼 어댑터. Claude용, OpenAI 호환(Gemma 4)용, 테스트용 가짜가 있다
후보(candidate)같은 요청으로 여러 번 생성한 테스트 파일 중 하나. 여러 후보를 만들어 모두 빌드해 보고 통과한 것을 고른다
Preflight(사전검증)테스트 본문 없이 뼈대와 스텁만으로 빌드가 되는지 먼저 확인하는 단계. 환경 문제와 생성 문제를 분리한다
실행 기록(run)genut gen 한 번의 모든 산출물과 로그가 담긴 디렉터리
3전체 흐름

3.1 그림으로 보기

각 단계를 펼쳐 보면 다음과 같습니다.

1
분석코드(libclang) + Analyzer 에이전트
함수 시그니처, 타입, 호출 심볼, 전역, include, static 여부를 뽑고 호출 심볼마다 "링크 시 정의가 있는가"를 판정
실패: 플래그를 못 찾거나 파싱이 깨지면 종료. Analyzer의 "테스트 불가" 판정은 코드가 확인한 결정적 신호(인라인 어셈블리뿐, 컴파일 DB 항목 없음, 빈 함수)가 있을 때만 종료 사유가 되고, 없으면 경고로 기록하고 진행
2
스텁Stub Planner 에이전트 + 스텁 도구
"정의 없음" 심볼과 규칙상 반드시 가짜로 바꿔야 하는 심볼을 스텁 도구로 생성
실패: 실패한 심볼은 기록하고 그 경로는 "범위 축소" 대상으로 표시
3
사전검증 (Preflight)코드
케이스가 없는 빈 테스트 파일(include, 스위트 선언, 스텁 연결만)을 실제로 빌드
실패: 환경 오류로 종료. LLM을 한 번도 부르지 않음. 사람이 고쳐야 할 문제
4
스모크Test Writer 에이전트 + 코드 검증
가장 단순한 케이스 하나만 담은 테스트 파일을 N개 생성하고 검증. 후보들의 케이스를 한 파일로 합쳐 한 번에 검증하고 통과한 케이스를 취함(4.4). 빌드가 느린 환경(KUnit/QEMU)에서는 생략하고 의미 검사가 역할을 대신함 (7.7)
실패: 수정 루프로. 예산을 다 써도 안 되면 포기하고 가장 진전된 후보와 진단을 남김
5
확장Test Writer 에이전트
규칙 md의 커버리지 기준(정상·오류·경계)에 따라 케이스를 추가 생성하고 검증
실패: 실패한 케이스만 수정 루프로. 통과한 케이스는 보존
6
수정코드 분류 + Fixer 에이전트 + 코드 검증
실패 케이스마다 코드가 실패를 분류 → Fixer가 정해진 전략 중 하나 선택 → 그 케이스만 재작성 → 재검증
한도 초과: 케이스당 수정 2회를 넘기면 그 케이스 제거. 전체 4라운드를 넘기면 남은 실패 케이스 모두 제거. 사유는 리포트에. 어느 경우에도 이미 통과한 케이스는 유지(7.10)
7
커버리지코드 수집·조건 추출 + Test Writer + Analyzer
통과 케이스로 실행한 결과에서 대상 함수의 미커버 줄을 뽑고, 줄마다 도달 조건(가장 가까운 분기의 조건식과 방향)을 붙여 그 줄을 실행시키는 케이스를 요청. 목표는 라인 커버리지 100% (7.6)
실패: 새 케이스가 실패하면 수정 루프로. 라운드(기본 3)를 넘기면 남은 미커버 줄을 "도달 불가 사유"와 함께 리포트에 남김
8
리뷰코드의 결정적 검사(7.9) + Reviewer 에이전트
단정 없음·항상 참·금지 패턴·실제값 베끼기는 코드가 즉시 검사(7.9). Reviewer는 규칙 준수, "항상 참인 단정" 같은 무의미한 테스트, 수정 과정에서 단정을 무력화해 억지로 통과시킨 흔적, 커버리지용 케이스가 단정 없이 줄만 밟는지 검사
지적: 해당 케이스를 1회 수정하거나 제거. 수정은 빌드 예산 안에서만, 제거로 커버리지가 떨어지면 리포트에 재계산
✓
최종 확인 + 리포트코드
리뷰까지 끝난 최종 파일(통과 케이스만)을 그대로 한 번 더 빌드·실행해 확인한 뒤 함수별 테스트 파일을 쓴다. 일부만 통과해도 통과분은 살린다(7.10). 리포트에는 함수별 complete/partial/none, 제거 케이스와 사유, 소스 버그 의심 목록, 모든 프롬프트·로그·판정

3.2 왜 이렇게 나눴나

  • LLM 호출 전에 걸러 낸다: 1·2·3단계는 LLM이 거의 개입하지 않는다. 환경 문제로 LLM을 반복 호출하는 낭비를 막는다.
  • 작게 시작해서 키운다: 4→5 순서 덕분에 "빌드 자체가 안 되는 문제"와 "특정 케이스의 논리 문제"를 분리해서 다룬다.
  • 케이스는 독립적이다: 5·6·7단계에서 케이스 하나가 실패해도 다른 케이스는 영향을 받지 않는다. 최종 결과는 "통과한 케이스의 집합"이다.
  • 커버리지는 마지막에 채운다: 먼저 규칙의 최소 케이스로 빌드·통과를 확보하고, 그 위에서 미커버 줄만 겨냥한 케이스를 추가한다. 처음부터 100%를 요구하면 실패 원인이 섞인다.
  • 테스트 파일은 함수별로, 빌드는 묶어서: 테스트 파일은 함수마다 하나씩 만들되, 같은 소스 파일의 함수들은 라운드마다 한 번에 빌드한다(7.8). 느린 커널 빌드에서 시간을 결정하는 요소다.
  • 통과한 것은 끝까지 살린다: 일부 케이스만 통과해도 그 케이스들로 최종 파일을 만들고, 마지막에 한 번 더 빌드·실행해 확인한다(7.10).
4역할별 에이전트

4.1 왜 역할을 나누나

LLM 하나에 "이 함수 테스트 만들어서 빌드까지 통과시켜"라고 하면 다음 문제가 생깁니다.

  • 한 번에 생각할 것이 너무 많아 품질이 떨어진다. 특히 Gemma 4 같은 중형 모델에서 심하다.
  • 어디서 잘못됐는지 추적하기 어렵다.
  • 프롬프트 하나를 고치면 다른 부분이 망가진다.

역할을 나누면 각 에이전트는 작은 입력을 받아 정해진 형식의 작은 출력을 냅니다. 입력과 출력은 모두 구조화(JSON 스키마)되어 있어 코드가 검증하고 기록할 수 있습니다.

정리하면 GenUT는 LLM 에이전트 여섯 개(Analyzer, Stub Planner, Test Writer, Fixer, Reviewer, Note Keeper)와 LLM이 아닌 오케스트레이터로 이루어진 멀티 에이전트 구조입니다. 에이전트끼리 자유롭게 대화하는 방식이 아니라, 오케스트레이터가 단계마다 필요한 에이전트만 부르고 결과를 공유 상태(블랙보드)에 쌓아 다음 에이전트에게 넘기는 파이프라인 + 블랙보드 방식입니다. 그래서 어느 에이전트가 무엇을 받고 무엇을 냈는지 항상 기록에 남고, Gemma 4처럼 긴 대화에 약한 모델에서도 안정적으로 동작합니다.

4.2 역할 목록

각 역할이 받는 것과 내는 것, 지켜야 할 것입니다. 호출 시점은 그림 3-1, 오케스트레이터·도구와의 관계는 그림 3-2를 보세요.

역할받는 것내는 것지켜야 할 것
Analyzer코드가 만든 분석 보고서테스트 가능 여부, 주의 사항(예: "두 번째 인자는 반드시 정렬된 배열"), 추천 케이스 목록보고서에 없는 사실을 지어내지 않는다. 불확실하면 "확인 필요"로 표시

Orchestrator(LLM 아님) 위 에이전트를 순서대로 호출하고 예산을 관리하는 Python 코드

4.3 에이전트 호출의 공통 구조

시스템 프롬프트 = 역할 설명(짧게) + 공통 규칙 md + 백엔드 규칙 md + (해당 시) 스텁 도구 md
유저 프롬프트   = 이번 호출의 입력(구조화 텍스트) + 출력 형식(JSON 스키마)
응답           = JSON (스키마 검증 → 실패 시 오류 메시지와 함께 최대 2회 재요청)

호출마다 프롬프트와 응답 전문이 실행 기록에 저장되어 나중에 그대로 볼 수 있습니다(11장).

4.4 Gemma 4를 위한 배려

  • 역할 설명은 짧게, 예시는 하나만. 긴 시스템 프롬프트는 중형 모델에서 지시 누락을 만든다.
  • 선택은 열거형으로. "어떻게 고칠지 자유롭게 말해 봐" 대신 "다음 다섯 가지 중 하나를 골라".
  • 출력은 전체 케이스 소스. 부분 패치(search/replace)는 정확한 문자열 일치가 필요해 중형 모델이 자주 실패한다. 케이스 하나는 수십 줄이라 전체를 다시 쓰는 비용이 작다.
  • 후보 다중 생성. 사내 API는 호출 비용이 낮으므로 온도를 약간 올려 N개를 만들고 전부 검증한다. 후보는 파일 단위로 고르지 않고 케이스 단위로 합친다. 후보들의 케이스에 고유 이름을 붙여 한 파일로 묶어 한 번에 검증하고, 통과한 케이스의 합집합을 취한다. 같은 목적의 케이스가 여럿 통과하면 하나만 남긴다.
5규칙 md 작성 가이드

5.1 어떤 것을 규칙으로 쓰나

규칙 md는 사람이 GenUT에 주는 유일한 지시문입니다. "꼭 지켜야 할 것"만 적고, 나머지는 에이전트가 판단하게 둡니다.

규칙으로 써야 하는 것에이전트에 맡겨도 되는 것
네이밍 규칙 (test_<func>_<situation>)케이스를 몇 개 만들지
절대 금지 (실제 하드웨어 접근, 전역 상태 변경, sleep)어떤 경계값을 시험할지
반드시 스텁해야 하는 심볼/패턴 (readl, writel, *_hw_*)스텁 반환값을 무엇으로 할지
메모리 관리 규칙 (KUnit: kunit_kzalloc만 사용)구조체 초기화 방식
커버리지 최소 기준 (정상 1 + 오류 경로 1 + 경계 1)그 이상의 케이스
테스트 파일 위치와 이름 (tests/<src>_<func>_test.cc)
리뷰에서 거부할 패턴 (EXPECT_TRUE(true))

5.2 파일 구성

$GENUT_HOME/rules/            # 공통: 모든 프로덕트에 적용
├── common.md    # 두 백엔드 공통. 네이밍, 금지, 커버리지 기준, 출력 형식
├── gtest.md     # gtest 전용. fixture 사용 여부, 매처 선호, 파일 위치
└── kunit.md     # KUnit 전용. 메모리 규칙, 스위트/모듈 매크로

$GENUT_HOME/products/<이름>/rules/   # 프로덕트 추가 규칙. 공통 뒤에 덧붙이며 충돌 시 프로덕트 우선
├── common.md
├── gtest.md
└── kunit.md

프롬프트에는 "공통 규칙"과 "이 프로덕트 규칙"을 구분해 넣습니다(11.5). 스텁 도구 사용법 md(stub-tools/)는 규칙과 별개로 Stub Planner와 Test Writer에게만 들어갑니다.

5.3 작성 요령

  • 한국어로: 규칙 md는 한국어로 쓴다. 프롬프트에 그대로 삽입되며, 역할 지시문(영어)과 섞여도 동작하도록 설계한다. 효과는 genut eval로 확인한다.
  • 짧게: 전체 규칙이 모델 컨텍스트의 일부를 차지한다. common + 백엔드 합쳐 100줄 이내를 권장한다.
  • 예시 하나씩: "이렇게 쓰라"는 좋은 예 하나가 긴 설명보다 낫다.
  • 금지는 명시적으로: "하지 말 것" 목록은 Reviewer가 그대로 검사 항목으로 쓴다.
  • 바꾸면 측정: 규칙을 바꾼 뒤 genut eval로 성공률 변화를 확인한다(11장).

5.4 예시 (rules/kunit.md 일부)

# KUnit 규칙

## 반드시
- 메모리 할당은 kunit_kzalloc(test, ...)만 사용한다. kmalloc/kfree 직접 호출 금지.
- 테스트 이름: test_<함수명>_<상황>. 예: test_rb_push_when_full
- 스위트 이름: <소스파일명>_<함수명>_test
- static 함수 접근은 스텁 도구가 제공하는 방식을 따른다 (docs/stub-tools/kunit-stub.md 참고).

## 절대 금지
- readl/writel/ioremap 등 MMIO 직접 호출. 반드시 스텁 도구로 대체.
- msleep/udelay. 시간 의존 테스트는 만들지 않는다.
- 전역 변수 직접 수정. 필요하면 setup/teardown 에서 복원.

## 커버리지 최소
- 정상 경로 1개, 오류 반환 경로 1개, NULL 또는 경계값 1개.
6정적 분석

6.1 목표

LLM이 "추측"할 여지를 최대한 없애는 것이 목표입니다. 테스트가 빌드에 실패하는 가장 흔한 이유는 include 누락, 잘못된 타입, 정의 없는 심볼 호출입니다. 이 세 가지는 모두 코드가 정확히 계산할 수 있습니다.

6.2 compile_commands.json: 두 백엔드 공통 입력

gtest (CMake)KUnit (커널)
생성 방법cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ONmake compile_commands.json (커널 5.10+)
담긴 것소스별 컴파일 명령 전체소스별 컴파일 명령 전체 (gcc 전용 플래그 다수)
문제거의 없음libclang이 모르는 gcc 전용 옵션이 많아 그대로 쓰면 파싱 실패

커널 플래그 정제기(flag_sanitizer.py)가 커널 명령에서 libclang이 받아들이는 것만 남깁니다.

  • 유지: -I, -isystem, -D, -U, -include, -std=, -nostdinc, --target=, -m32/-m64, clang이 아는 -f 옵션
  • 제거: -mno-fp-ret-in-387, -fconserve-stack, -mindirect-branch=*, -fno-allow-store-data-races, clang이 모르는 -Wno-*, -o, 입력 파일 이름 등
  • 제거 목록은 flag_sanitizer.yaml로 관리해 코드 수정 없이 추가할 수 있다. 정제 결과로도 파싱이 실패하면 오류 메시지에서 "unknown argument"를 찾아 그 플래그를 자동으로 빼고 1회 재시도한다.

테스트 파일의 플래그: 새로 만들 테스트 파일은 아직 compile DB에 없습니다. 대상 소스와 같은 디렉터리의 항목(커널은 같은 Makefile 아래) 플래그를 빌려 씁니다.

폴백: compile_commands.json이 없으면 커널은 .<file>.o.cmd 파일을 직접 파싱합니다. CMake 프로젝트는 생성 방법을 안내하고 멈춥니다.

6.4 링크 범위 판정 (linkscope)

테스트가 "링크 단계"에서 실패하는 이유는 거의 항상 정의가 없는 심볼을 호출하기 때문입니다. 호출 심볼마다 다음 중 하나로 판정합니다.

판정뜻조치
same_tu대상 소스 파일 안에 정의가 있음그대로 사용
linkable테스트가 링크하는 타깃(gtest: link_targets, KUnit: 아래 기준)에 정의가 있음그대로 사용하되 부작용(하드웨어 등)이 있으면 규칙에 따라 스텁
externallibc, 커널 코어 API 등 항상 링크되는 것그대로 사용
undefined어디에도 정의가 없거나 테스트 빌드에 포함되지 않음스텁 필수
must_stub규칙 md의 "반드시 스텁" 패턴에 해당스텁 필수

판정 근거(어느 파일에서 정의를 찾았는지)도 기록해 뷰어에서 볼 수 있게 합니다.

gtest의 판정 기준: 테스트 실행 파일이 링크하는 사용자 타깃([gtest] link_targets, 7.5)에 속한 소스에 정의가 있으면 linkable입니다. 타깃과 소스의 대응은 CMake File API(<build>/.cmake/api/v1)의 codemodel에서 읽습니다.

KUnit의 판정 기준: 커널에서는 "링크 가능"이 테스트의 빌드 형태에 따라 달라집니다.

상황판정
테스트가 built-in(obj-y)이고 심볼이 vmlinux에 들어가는 파일에 있음linkable
테스트가 모듈(obj-m)이고 심볼이 EXPORT_SYMBOL/EXPORT_SYMBOL_GPL로 내보내짐linkable
테스트가 모듈이고 심볼이 내보내지지 않음undefined → 스텁 필수
심볼이 정의된 파일이 현재 .config에서 빌드되지 않음(obj-$(CONFIG_X)가 꺼짐)undefined
심볼이 static스텁 도구의 static 접근 방식(10장)

테스트의 빌드 형태는 test_file이 등록된 Makefile 줄(obj-y/obj-m/obj-$(CONFIG_...))과 .config에서 읽습니다.

7빌드·실행 실패 대응

이 장이 성공률을 결정합니다. 실패를 막고, 빨리 잡고, 정확히 진단하고, 좁게 고치는 네 층으로 다룹니다.

7.1 막기: LLM 호출 전에

  • Preflight (3장 ③): 뼈대만으로 빌드. 환경 문제를 LLM 루프 밖으로 뺀다.
  • 사실 확정 (6장): include, 시그니처, 타입, 상수, 스텁 필수 심볼을 코드가 계산해 프롬프트에 넣는다.
  • 뼈대 제공: 백엔드별 최소 뼈대(include 블록, 스위트 선언, 스텁 연결, 모듈 매크로, KUnit 케이스 테이블)는 코드가 케이스 목록에서 만든다. 대상 함수가 전역을 쓰면 케이스별 리셋 훅도 뼈대에 넣는다. LLM은 케이스 본문만 쓴다.

7.2 빨리 잡기: 단계별 검증

빌드는 비싸다. 특히 커널 빌드는 분 단위다. 그래서 검증을 네 단계로 나누고 앞 단계가 깨끗할 때만 다음으로 갑니다.

단계하는 일걸리는 시간잡는 것
1. 의미 검사libclang으로 테스트 파일을 같은 플래그로 파싱 (빌드 없음)초 단위include 누락, 오타, 타입 불일치, 선언 없는 식별자
2. 컴파일오브젝트 파일만 생성초~수십 초1단계가 놓친 컴파일 오류
3. 링크실행 파일/모듈 생성초~분정의 없는 심볼
4. 실행테스트 실행초~분단정 실패, 크래시, 타임아웃

1단계는 LLM 응답 직후 바로 돌릴 수 있어서, 흔한 실수의 대부분을 몇 초 안에 되돌려 줍니다.

경고 정책: 컴파일 DB에 -Werror가 있거나 커널이 CONFIG_WERROR=y이면 실제 빌드는 경고도 오류입니다. 의미 검사도 같은 기준으로 경고를 오류로 보고하고 warning_as_error로 분류해 Fixer에 넘깁니다. 생성 테스트에서 가장 흔한 것은 미사용 변수·미사용 결과(-Wunused-*)와 부호 비교(-Wsign-compare)이며, 전용 프롬프트에 "경고를 끄지 말고 코드를 고치라"를 명시합니다.

단정 실패의 특별 취급

단정 실패는 "테스트가 틀렸을 수도, 소스가 틀렸을 수도" 있습니다. 기본 입장은 테스트가 틀렸을 가능성이 높다입니다(소스는 보통 이미 동작하는 코드이므로). 하지만 다음 조건이면 소스 버그를 의심합니다.

  • 소스의 반환 지점 목록(6장)으로 보아 기대값이 명백히 소스 의도와 일치하는데 실제값이 다를 때
  • 같은 케이스를 두 번 고쳤는데도 실제값이 소스 의도와 계속 다를 때

이때 Fixer는 drop_case를 선택하고 suspected_bug: true와 사유를 적습니다. 리포트의 "소스 버그 의심" 목록에 올라가며, 사람이 확인할 가치가 있는 발견입니다. 이 목록은 프로덕트 지식(suspected_bugs.md)에 함수 본문 해시와 함께 저장되어, 같은 함수를 다시 생성할 때 같은 케이스를 또 시도하지 않도록 참고합니다(11.5). 기대값을 실제값으로 바꿔서 억지로 통과시키는 것은 Reviewer가 거부합니다.

7.4 좁게 고치기

케이스 단위 단조 진행

테스트 파일은 독립 케이스의 집합입니다. 각 케이스는 상태를 가집니다.

  • pass가 된 케이스는 이후 어떤 재작성에서도 글자 하나 바뀌지 않는다. Fixer 프롬프트에 "다음 케이스는 그대로 유지"라고 명시하고, 응답을 받은 뒤 코드가 diff로 확인한다. 바뀌었으면 원본으로 되돌린다.
  • 재작성 단위는 케이스 하나. 파일 전체를 다시 쓰더라도 바뀌는 부분은 그 케이스뿐이다.
  • 최종 산출물은 pass 케이스만 담은 파일이며, 최종 확인 빌드(7.10)를 거친다. 일부 케이스만 통과해도 그 케이스들은 살린다.

공유 영역의 변경 규칙

케이스 밖에도 여러 케이스가 함께 쓰는 것이 있습니다. include 블록, 헬퍼 함수(예: 7.3의 make_rb), fixture·init/exit 코드, 스텁의 기본 동작이 그것입니다. 이를 공유 영역이라 부르고 케이스와 별도 상태로 관리합니다. 공유 영역이 바뀌면 글자 하나 안 바뀐 통과 케이스도 회귀할 수 있기 때문입니다.

  • 공유 영역의 변경은 케이스 하나의 수정이 아니라 전체에 대한 수정이다. 변경 뒤에는 모든 pass 케이스를 한 빌드로 다시 검증한다.
  • 재검증에서 회귀한 케이스가 있으면 공유 영역 변경을 되돌리고, Fixer에게 "공유 영역을 바꾸지 않는 방법"을 요구한다. 그래도 원래 실패 케이스가 남으면 그 케이스는 drop_case.
  • 스텁의 동작은 가능하면 케이스 안에서 설정한다(스텁 도구가 케이스별 반환값 설정을 지원하는 경우). 기본 동작을 바꾸는 add_stub는 공유 영역 변경으로 취급한다.
  • 헬퍼 함수는 Test Writer가 제안할 수 있지만 코드가 공유 영역으로 분리해 저장하고 어떤 케이스가 쓰는지 추적한다. 쓰는 케이스가 모두 제거되면 헬퍼도 제거한다.
  • 뼈대(include, 스위트 선언, KUnit 케이스 테이블, 모듈 매크로)는 항상 코드가 케이스 목록에서 다시 만든다. LLM은 뼈대를 쓰지 않는다.

전략 사다리

Fixer가 고를 수 있는 전략은 다섯 가지이고, 올라갈수록 "덜 고치고 더 포기"합니다.

전략뜻언제
fix_case케이스 소스를 고친다컴파일 오류, 기대값 오류
add_stub스텁을 추가/수정하고 케이스를 그에 맞게 고친다미정의 참조, 스텁 반환값 때문에 생긴 크래시
drop_case이 케이스를 버린다수정 한도 초과, 소스 버그 의심, 크래시 재발
narrow_scope테스트 범위를 줄인다(예: 특정 경로는 다루지 않음)스텁 불가 심볼을 거치는 경로
give_up이 함수에 대한 새 시도를 멈춘다. 이미 통과한 케이스는 유지한다(7.10)스모크조차 통과 못 함, 예산 소진

분류기가 권장 시작 전략을 주고, Fixer는 그보다 아래로 내려갈 수 없습니다(예: 권장이 add_stub이면 fix_case는 선택 불가). 이 제약이 "같은 수정을 반복하며 예산을 태우는" 패턴을 막습니다.

7.5 gtest 특화: 테스트 타깃 구성

전제: 테스트 대상 소스는 이미 사용자 빌드(CMake 타깃)에 포함되어 있습니다. GenUT는 대상 소스를 다시 컴파일하지 않고, 사용자 타깃을 링크하는 테스트 실행 파일을 만듭니다.

항목설계
테스트 타깃GenUT가 관리하는 CMakeLists.txt는 테스트 파일을 glob으로 찾아 파일마다 실행 파일 타깃(genut_<src>_<func>)을 만든다. 작업 중에는 이 파일과 테스트 파일을 전용 빌드 디렉터리 안(genut-src/)에만 두고, 최상위 project() 직후 실행되는 주입 파일(CMAKE_PROJECT_INCLUDE)이 최상위 처리가 끝날 때 그것을 include한다. 그래서 GenUT 빌드에는 사용자의 수정이 필요 없고, 프로덕트 트리는 설치 전까지 그대로다(11.2). 설치 때 같은 CMakeLists를 [gtest] cmake_lists_dir에, 함수별 테스트 파일을 [gtest] output_dir에 쓴다(7.8). 사용자가 루트에서 add_subdirectory로 한 번 연결하면 사용자 빌드에서도 같은 테스트가 빌드되며, GenUT 빌드는 그 설치본을 건너뛴다
링크[gtest] link_targets에 적힌 사용자 타깃을 링크한다. 비어 있으면 CMake File API로 대상 소스가 속한 타깃을 찾아 그 테스트 파일에만 쓴다(소스 파일마다 속한 라이브러리가 다르므로). 테스트별 링크 타깃은 관리 디렉터리의 genut_links.cmake에 남고, 설치는 그 함수의 항목만 갱신한다. linkable 판정(6.4)도 같은 정보(링크 타깃과 의존 타깃의 소스)로 한다
전용 빌드 디렉터리[gtest] cmake_build_dir(기본 build-genut)를 GenUT가 구성한다. 사용자 빌드 디렉터리는 건드리지 않는다. 구성 시 커버리지 플래그(--coverage 또는 llvm 계열), 선택한 새니타이저, coverage_opt_level을 CMAKE_C_FLAGS/CMAKE_CXX_FLAGS에 넣으므로 대상 소스도 계측된 채 빌드된다. compile_commands.json은 이 디렉터리 것을 쓴다
C 소스를 C++ 테스트에서뼈대의 include 블록을 extern "C" { ... }로 감싼다. 대상 헤더가 C++에서 컴파일되지 않으면(예: new를 식별자로 사용) header_not_cpp_clean으로 분류해 사람에게 안내한다
스텁과 실제 정의의 충돌링크된 타깃에 이미 정의가 있는 심볼을 스텁하면 중복 정의가 난다. 심볼 교체 방식(--wrap, weak 심볼, objcopy 등)은 스텁 도구 md가 정하며, GenUT는 duplicate_symbol 분류로 잡아 Stub Planner에 "이 심볼은 스텁 도구의 교체 방식 필요"로 전달한다
실행--gtest_output=json으로 케이스별 결과와 기대값/실제값을 받는다. --gtest_filter=Suite.Case로 케이스 격리. 실행은 임시 작업 디렉터리에서 test_timeout_sec 안에 하고, 생성된 코드가 호스트를 건드리지 않도록 "작업 디렉터리 밖 파일·네트워크 접근 금지"를 기본 규칙 md에 둔다
크래시새니타이저 리포트 또는 gdb 배치 백트레이스로 크래시 브리프를 만든다(8.3). 새니타이저는 -fno-sanitize-recover로 첫 리포트에서 멈추게 한다. UBSan은 기본으로 계속 실행해 정의되지 않은 동작을 한 케이스가 통과로 끝날 수 있기 때문이다

7.6 라인 커버리지 100% 목표

7.7 느린 빌드 환경 대응 (KUnit, QEMU 약 8분)

KUnit 빌드·실행은 QEMU에서 1회 약 8분이 걸립니다. 빌드 횟수가 곧 소요 시간이므로 다음을 적용합니다.

  • 예산을 빌드 횟수로 표현: max_builds_per_run(KUnit 기본 10). 시작 시 "예상 최대 80분"을 터미널에 보여 준다.
  • 빌드 전에 최대한 걸러 내기: 1단계 의미 검사(초 단위)를 통과한 후보만 빌드한다. 후보가 여러 개면 의미 검사를 통과한 것만 남기고, 그 케이스들을 한 파일에 합쳐 한 번에 빌드한다.
  • 스모크 단계 생략: 사전검증 빌드 시간이 slow_build_threshold_sec(기본 120초)를 넘으면 스모크(4)를 건너뛰고 확장(5) 케이스를 바로 만든다. 의미 검사가 스모크의 역할(빌드 오류 조기 발견)을 대신한다.
  • 사전검증 캐시: 뼈대+스텁, .config, compile_commands.json, 실행 스크립트의 해시가 이전 실행과 모두 같으면 사전검증 빌드를 건너뛴다. 사전검증은 스크립트를 --mode build로만 부른다.
  • 크래시 격리 제한: max_isolation_runs KUnit 기본 2. 1차 용의자("마지막으로 시작된 케이스")만 재실행하고, 재현되지 않으면 용의자를 제거하고 넘어간다.
  • 수정 라운드 묶기: 한 라운드에서 실패한 케이스를 모두 고친 뒤 한 번에 빌드한다. 케이스별로 빌드하지 않는다.
  • 커버리지는 항상 함께 수집: 별도 커버리지 실행이 없다.

예상 빌드 횟수(KUnit, 함수 1개, 정상 경로): 사전검증 1 + 확장 1 + 수정 1~2 + 커버리지 1~2 + 최종 확인 1 = 5~7회, 약 40~56분. 함수가 여럿이면 7.8의 묶음 빌드로 함께 처리합니다.

7.8 함수별 테스트 파일과 묶음 빌드

입력 단위는 "파일 + 함수"이고, 함수를 생략하면 파일의 모든 비static 함수가 대상입니다. 테스트 파일은 gtest와 KUnit 모두 함수마다 하나씩 만듭니다. 다만 빌드와 실행은 함수마다 따로 하지 않고 같은 소스 파일의 함수들을 라운드마다 한 번에 묶어서 합니다. 함수마다 따로 빌드하면 KUnit에서는 함수 10개에 5시간이 넘기 때문입니다.

gtestKUnit
테스트 파일<output_dir>/<src>_<func>_test.cc (test_file_pattern)<test_dir>/<src>_<func>_test.c (test_file_pattern)
스위트함수당 1개함수당 1개 (<src>_<func>_test)
빌드 등록GenUT가 관리하는 CMakeLists.txt에 함수마다 실행 파일 타깃(genut_<src>_<func>)을 둔다. 한 라운드의 타깃들을 cmake --build 한 번으로 빌드한다사용자가 Makefile/Kconfig에 한 번만 등록한 집합 파일([kunit] test_file)의 내용을 GenUT가 생성한다. 집합 파일은 공유 영역(include, 스텁 연결), 함수별 파일의 #include, 모든 스위트를 담은 kunit_test_suites(...) 한 줄로 이루어진다
실행함수별 실행 파일을 차례로 실행한다. 한 함수의 크래시가 다른 함수에 영향을 주지 않는다한 빌드·한 부팅에서 모든 스위트가 실행된다. 스크립트는 포함된 테스트를 모두 실행한다. 앞 케이스가 크래시하면 뒤 케이스는 not_run(7.10)
이름 충돌실행 파일이 달라 없다함수별 파일이 집합 파일 안에서 한 번역 단위로 합쳐진다. 그래서 함수별 파일의 헬퍼·전역은 코드가 static과 함수 접두어로 만들고, 같은 심볼의 스텁은 집합 파일에 한 번만 둔다. 의미 검사(7.2)도 집합 파일 기준으로 한다
  • 분석(1)과 스텁 계획(2)은 함수마다 한다. 스텁은 소스 파일 단위로 합친다(같은 심볼은 한 번만).
  • 사전검증(3)은 실행당 1회.
  • 작성(4·5), 수정(6), 커버리지(7)는 라운드마다 모든 함수의 케이스를 모아 한 번 빌드한다. LLM 호출은 프롬프트를 작게 유지하기 위해 함수별로 한다.
  • 케이스 상태(TestCase)는 target_function 필드를 가진다. 빌드 횟수·시간 예산은 실행 단위(한 실행 = 소스 파일 하나, max_builds_per_run, max_seconds_per_run), 토큰·수정 횟수 예산은 함수 단위다.
  • 한 함수가 예산을 다 써도 다른 함수의 진행은 계속된다. 리포트는 함수별 결과와 소스 파일 전체 커버리지를 함께 보여 준다.
  • 함수 하나만 지정했을 때도 같은 경로를 쓴다.
  • 이전 실행에서 만든 함수별 파일: genut gen은 대상 함수의 파일만 새로 쓰고 다른 함수의 파일은 건드리지 않는다. KUnit 작업 중 빌드에는 이번 실행의 대상 함수 파일만 집합 파일에 넣어 이전 파일의 영향을 받지 않게 한다. 최종 확인(7.10)에서는 이전 파일까지 포함한 최종 집합으로 한 번 검증하고, 그때 실패한 이전 파일은 집합 파일에서 빼고 "기존 테스트 회귀"로 리포트한다. gtest는 함수별 실행 파일이 따로라 이전 파일을 다시 검증하지 않는다.

예상 빌드 횟수(KUnit, 함수 10개 파일): 사전검증 1 + 확장 1 + 수정 2~3 + 커버리지 2~3 + 최종 확인 1 = 7~9회, 약 56~72분. 함수별로 따로 빌드했을 때의 40~60회와 비교됩니다.

7.10 부분 성공 보존과 최종 확인

여러 번 생성·빌드·실행을 반복해도 모든 케이스가 통과하지 못하는 경우는 흔합니다. 이때 통과한 케이스는 반드시 살려서 최종 파일로 남깁니다. 이 절은 그 보장을 지키는 방법입니다.

원칙

  • 결과는 "모두 통과"가 아니라 "통과한 케이스의 집합"이다. 함수별 결과는 셋 중 하나다.
    • complete: 커버리지 목표를 달성했고, 실패로 제거된 케이스가 없다(소스 버그 의심 제외).
    • partial: 통과 케이스가 1개 이상이지만 실패·제거·미실행 케이스가 있다. 이것도 성공한 실행이며 테스트 파일이 만들어진다.
    • none: 통과 케이스가 없다.
  • 어떤 종료 경로에서도 통과 케이스를 잃지 않는다. 정상 종료, 예산 소진(토큰·빌드·시간), give_up, Reviewer 지적, infra_error, 사용자 중단(Ctrl+C), GenUT 내부 예외가 모두 해당한다.
  • give_up은 "이 함수에 대한 새 시도를 멈춘다"는 뜻이다. 이미 통과한 케이스는 그대로 최종 파일로 간다.
  • 케이스 상태는 빌드가 끝날 때마다 실행 기록의 state.json에 저장한다. GenUT가 중간에 죽어도 그때까지의 통과 케이스가 남는다.
  • 통과 케이스가 0이면 프로덕트 위치에 파일을 쓰지 않는다. 가장 진전된 후보와 진단은 실행 기록에 남는다.

케이스 상태 보강

  • not_run: 다른 케이스의 크래시·타임아웃으로 이번 빌드에서 실행되지 못한 케이스. 실패가 아니므로 수정 횟수를 쓰지 않고 다음 빌드에서 다시 실행한다. 끝까지 실행되지 못하면 "미실행"으로 리포트하고 최종 파일에서 뺀다.
  • flaky: 한 번 통과한 케이스가 케이스 소스와 공유 영역이 바뀌지 않았는데 다른 빌드에서 실패한 경우. 다음 빌드에서 다시 확인해 또 실패하면 불안정 케이스로 최종 파일에서 빼고 리포트한다. 공유 영역이 바뀐 뒤의 실패는 7.4의 되돌리기 규칙을 따른다.

최종 확인 빌드

최종 파일은 pass 케이스만 담지만, 그 조합 그대로는 한 번도 빌드되지 않았을 수 있습니다. 실패 케이스와 함께 돌던 상태에서 통과했기 때문입니다. 실패 케이스를 빼도 보통은 문제가 없지만, KUnit에서 크래시 뒤에 가려졌던 케이스나 순서 의존이 있으면 결과가 달라질 수 있습니다. 그래서 리뷰(8)가 끝난 뒤 최종 파일 그대로 한 번 빌드·실행해 확인합니다.

  • 빌드 예산 중 final_build_reserve(gtest 2, KUnit 1)는 최종 확인용으로 남겨 둔다. 수정·커버리지 루프는 예약분을 쓰지 않는다.
  • 실행 중 "포함된 케이스가 모두 통과한 빌드"가 나올 때마다 코드가 그 테스트 파일을 녹색 스냅샷(snapshots/)으로 저장한다.

일부 실패, 예약 빌드 남음실패 케이스를 빼고 다시 확인한다
일부 실패, 예약 빌드 없음최종 확인에서 통과한 케이스만으로 확정한다. 리포트에 "제거 뒤 재확인 못 함"을 표시한다
빌드 실패·실행 불가·중단가장 케이스가 많은 녹색 스냅샷을 쓴다. 스냅샷에 없는 통과 케이스는 실행 기록의 final/에 "미확인"으로 남긴다
녹색 스냅샷도 없음통과 케이스를 final/에 "미확인"으로 남기고 프로덕트 위치에는 쓰지 않는다(install_unverified = true면 표시와 함께 쓴다)

"미확인"으로 남은 케이스는 genut finalize <run>으로 최종 확인만 다시 해서 설치할 수 있습니다. LLM은 부르지 않습니다.

리포트는 함수마다 "통과 6 · 제거 2(사유) · 미실행 1 · 불안정 0 · 결과 partial · 최종 확인 OK"처럼 적습니다. genut eval도 partial을 따로 집계해 "일부라도 건진 비율"을 함께 봅니다.

8로그 축약과 크래시 브리프

8.1 문제

KUnit 실행 로그는 커널 부팅 메시지, 다른 스위트 결과, 디버그 출력이 섞여 수만 줄이 되기도 합니다. 크래시가 나면 oops 덤프(호출 스택, 레지스터, 코드 바이트)가 수백 줄 추가됩니다. 이걸 그대로 LLM에 주면 (a) 컨텍스트를 넘기고 (b) 중요한 한 줄이 묻히고 (c) 중형 모델은 호출 스택을 제대로 읽지 못합니다.

8.2 로그 축약기

실행 로그는 파일로만 받습니다(stdout으로 받지 않음). 코드가 다음 순서로 필요한 부분만 뽑습니다.

1단계: 우리 스위트만 남기기. KTAP 형식에서 # Subtest: <우리 스위트 이름> 블록만 추출. 다른 스위트, 부팅 메시지 제거.

2단계: 케이스별 결과와 실패 상세. 이 블록은 거의 그대로 유지합니다. 기대값·실제값이 수정의 핵심 단서입니다. ASSERTION FAILED(KUNIT_ASSERT_*)와 # <case>: ... timed out도 같은 방식으로 뽑습니다.

ok 1 test_rb_push_normal
not ok 2 test_rb_push_when_full
    # test_rb_push_when_full: EXPECTATION FAILED at tests/rb_test.c:34
    Expected rb_push(&rb, data, 8) == -ENOSPC, but
        rb_push(&rb, data, 8) == 0 (0x0)
        -ENOSPC == -28 (0xffffffe4)

3단계: 크래시 브리프 (8.3)

4단계: 크래시 직전 꼬리. 크래시 마커 직전 N줄(기본 30)의 dmesg. 우리 코드가 찍은 pr_err 등이 여기 있을 때가 많습니다.

토큰 상한 조립: 위 네 덩어리를 우선순위대로 넣되 상한(기본 4,000 토큰)을 넘지 않게 합니다. 넘치면 4→3→2 순으로 줄입니다. 1은 항상 유지.

제거 대상: Code: 바이트 덤프, 레지스터 덤프(RAX: ... RBX: ...), 같은 줄 반복([... N times]로 접음), 타임스탬프.

스크립트가 --filter suite.case를 지원하면 처음부터 적게 출력하게 합니다.

8.3 크래시 브리프

원시 oops 대신 코드가 만든 크래시 브리프를 LLM에 줍니다.

단계하는 일

책임 프레임Call Trace:에서 테스트 파일 또는 대상 소스 파일에 속한 첫 프레임을 찾는다. 커널 코어 프레임(__kasan_report, do_page_fault 등)은 건너뛴다
심볼화프레임이 func+0x1a/0x40 형태면 scripts/faddr2line vmlinux func+0x1a/0x40로 file:line을 얻는다. decode_stacktrace.sh가 있으면 로그 전체를 먼저 통과시킨다. 디버그 정보가 없으면 함수 이름까지만
소스 연결책임 줄의 소스를 가져오고, 그 줄에서 역참조되는 식(slot->len)을 찾아 그 변수가 어디서 왔는지(파라미터, 스텁 반환값, 전역) 6장의 분석 결과로 연결한다
가설분류별 템플릿에 관련 심볼을 채운다

gtest의 크래시 브리프: 유저 스페이스에서도 같은 형식으로 만듭니다. 세그폴트가 나면 gtest의 JSON 결과 파일이 써지지 않으므로, stdout의 마지막 [ RUN ] Suite.Case 줄로 1차 용의자를 정합니다. 새니타이저가 켜져 있으면 ASan/UBSan 리포트(ERROR: AddressSanitizer: heap-use-after-free ... #0 ... in func file:line)를 파싱해 분류(asan_uaf, asan_oob, ubsan_*)와 책임 프레임을 얻습니다. 새니타이저 없이 세그폴트가 나면 gdb -batch -ex run -ex bt로 한 번 더 실행해 백트레이스를 얻습니다([gtest] crash_backtrace = "gdb", gdb가 없으면 생략).

8.4 케이스 격리

크래시가 나면 커널(또는 프로세스)이 죽어서 어느 케이스에서 났는지 로그만으로 모를 때가 많습니다.

  1. KTAP에서 마지막으로 ok/not ok가 찍힌 케이스 다음 케이스를 1차 용의자로 본다.
  2. 확실하지 않으면 용의자 케이스만 다시 실행한다. gtest는 --gtest_filter로, KUnit은 스크립트가 --filter를 지원하면 --mode run으로 빌드 없이, 지원하지 않으면 용의자 케이스만 담은 파일을 써서 다시 빌드·실행한다. 재현되면 확정.
  3. 재현되지 않으면(순서 의존) 남은 케이스를 하나씩 실행한다. 비용이 크므로 max_isolation_runs(기본 4)로 제한한다.
  4. 범인 케이스에 fix_case 1회 → 실패하면 drop_case.

8.5 환경 권고

크래시 분석 난이도는 커널 빌드 설정에 크게 좌우됩니다. 문서와 genut doctor에서 다음을 권고합니다.

  • CONFIG_KASAN=y, CONFIG_UBSAN=y: 메모리 오류 원인이 로그에 명시됨
  • CONFIG_DEBUG_INFO=y: 호출 스택을 file:line으로 바꿀 수 있음
  • CONFIG_KUNIT_ALL_TESTS=n + kunit.filter_glob: 우리 스위트만 실행
  • CONFIG_GCOV_KERNEL=y + 대상 파일 GCOV_PROFILE_<obj> := y: 라인 커버리지 수집(7.6)
  • gtest: -fsanitize=address,undefined (설정으로 선택)

9.4 구조화 출력 공통 계층 (structured.py)

에이전트의 모든 출력은 pydantic 모델입니다. 이 계층이 모델을 JSON으로 받아 오는 방법을 Provider 능력에 따라 고릅니다.

  1. json_schema 지원 → 스키마를 넘겨 제약 디코딩. 거의 실패하지 않음.
  2. 미지원 → 프롬프트에 스키마와 예시를 넣고 응답에서 JSON 블록을 추출. 파싱·검증 실패 시 오류 메시지를 붙여 최대 2회 재요청.
  3. 그래도 실패 → 해당 에이전트 호출 실패로 기록하고 오케스트레이터가 재시도 또는 다음 전략으로.

전송 오류: HTTP 429/5xx, 타임아웃, 연결 끊김은 구조화 출력 실패와 별개로 Provider 계층이 처리합니다. 지수 백오프(1, 2, 4, 8초)로 최대 max_retries(기본 4)회 재시도하고, 그래도 실패하면 infra_error로 실행을 중단합니다. 재시도는 토큰 예산을 소모하지 않지만 시간 예산은 소모합니다. 응답이 출력 한도에 걸려 잘렸으면(finish_reason = length) 재시도하지 않고 구조화 출력 실패로 넘겨, 출력 예약(9.7)을 늘려 1회 재요청합니다.

코드가 든 출력: 테스트 소스를 JSON 문자열로 받으면 따옴표·개행 이스케이프에서 중형 모델이 자주 깨집니다. 제약 디코딩이 있으면 JSON은 유효하지만 코드 품질이 떨어질 수 있습니다. 그래서 두 형식을 모두 구현합니다. (a) 기본 code_format = "json": 케이스 목록 전체를 JSON 스키마로. (b) 대안 code_format = "fenced": 메타데이터(이름, 목적, 전략)는 JSON, 케이스 소스는 그 뒤에 케이스 이름을 붙인 펜스 블록으로. 코드가 둘을 같은 pydantic 모델로 합칩니다. 어느 쪽이 Gemma 4에서 성공률이 높은지 genut eval로 비교해 기본값을 정합니다(14단계).

Gemma 4가 둘 다 지원하므로 1번이 기본이지만, 2번 경로도 FakeProvider로 항상 테스트해 둡니다(다른 모델로 바꿀 때를 대비).

9.7 컨텍스트 한도 관리 (llm/prompt_builder.py)

조각별 예산(분석 보고서 3,000, 축약 로그 4,000, 지식 1,500 토큰)만으로는 부족합니다. 규칙 md, 스텁 도구 md, 통과한 케이스 전체 소스, 구조체 정의, 과거 수정 사례가 한 프롬프트에 모이는 Fixer 호출은 조각마다 예산을 지켜도 합이 한도를 넘을 수 있습니다. Gemma 4가 32k로 서빙될 때 입력이 넘치면 서버는 오류를 내거나 앞부분을 조용히 잘라 버립니다. 앞부분이 잘리면 시스템 프롬프트의 규칙이 사라져 결과가 엉뚱해지는데 원인을 찾기 어렵습니다. 또 테스트 파일 전체 재작성은 출력이 수천 토큰이라, 입력이 한도에 딱 맞으면 응답이 중간에 끊깁니다.

그래서 모든 에이전트 호출은 프롬프트 조립기를 거칩니다. 에이전트는 프롬프트 문자열을 만들지 않고 조각 목록을 냅니다. 조각마다 우선순위와 축약 방법이 붙어 있습니다.

우선순위조각넘칠 때
1 필수역할 지시문, 규칙 md(공통+프로덕트), 출력 스키마, 대상 함수 시그니처와 타입 정의줄이지 않음
2 축약 가능분석 보고서관련 구조체·열거형만 남김
2 축약 가능통과 케이스 소스이름과 시그니처만 남기고 "보존하라"는 지시로 대체
2 축약 가능축약 로그, 크래시 브리프로그 상한을 절반으로 낮춰 다시 축약 (8.2의 우선순위 유지)
2 축약 가능지식 노트, 수정 사례(fix_patterns)상위 N개만 (N을 줄임)
2 축약 가능스텁 도구 md사용법 핵심 절만 (md에 표시된 <!-- genut:core --> 구간)
3 생략 가능예시, 참고 코드 조각, 과거 시도 요약통째로 제거

조립 절차:

  1. 조각을 모두 넣고 count_tokens로 전체를 셉니다.
  2. 허용량 = max_context − output_reserve_tokens − 안전 여유(context_safety_margin). 예: 32,768 − 6,000 − 5% ≈ 24,400.
  3. 넘치면 3번 조각을 하나씩 빼고, 그래도 넘치면 2번 조각을 우선순위 역순으로 하나씩 축약하며 매번 다시 셉니다.
  4. 1번 조각만으로도 넘치면 LLM을 부르지 않고 context_overflow 실패로 기록합니다. 오케스트레이터는 narrow_scope로 넘어가고, 리포트에 "규칙 md 길이를 줄이라"는 안내를 남깁니다.
  5. 어떤 조각이 얼마나 잘렸는지 trace.jsonl에 기록하고 genut view의 호출 카드에 표시합니다. 규칙 md가 길어 매번 다른 조각이 잘리는 상황을 여기서 잡습니다.

토큰 세기: Gemma 4 토크나이저를 로컬에 둘 수 없는 환경을 고려해 기본은 보수적 추정입니다(영문 4자당 1토큰, 한글은 글자당 1.5토큰, 코드는 3자당 1토큰). genut doctor가 실제 API 응답의 usage와 추정치를 비교해 보정 계수를 $GENUT_HOME/knowledge/token_calibration.json에 기록하고, 이후 추정에 곱합니다. OpenAI 호환 서버가 /tokenize 엔드포인트를 제공하면(vLLM 등) token_counter = "api"로 추정 대신 그것을 씁니다. 추정치는 항상 실제보다 크게 잡습니다. Anthropic provider는 토큰 세기 API를 그대로 씁니다.

이렇게 하면 9.5의 "호출당 8k 이내"가 원칙이 아니라 코드가 보장하는 성질이 됩니다. Claude로 개발할 때는 한도가 커서 티가 나지 않지만 Gemma 4로 바꾸는 순간 가장 먼저 부딪히는 문제이므로 2단계(LLM 계층)에 함께 구현합니다.

10스텁 도구 연동

10.1 전제

gtest용과 KUnit용 자체 스텁 도구가 각각 따로 있습니다. 사용법은 사용자가 gtest-stub.md, kunit-stub.md로 제공하며, GenUT를 셋업할 때 두 md가 모두 제공됩니다. 공통 md는 $GENUT_HOME/stub-tools/에 두고, 프로덕트마다 다른 스텁 도구를 쓰면 $GENUT_HOME/products/<이름>/stub-tools/에 둔 것이 우선합니다(11.5). 개발 단계에서는 연동 지점만 정의하고 NoopStub으로 테스트하며, 어댑터 구현은 md를 받은 뒤 합니다.

두 스텁 도구 모두 static 함수에 접근할 수 있습니다. 따라서 static 대상 함수를 직접 호출하거나 static 호출 심볼을 스텁하는 방법은 GenUT가 따로 만들지 않고 스텁 도구에 맡깁니다. 구체적인 사용법(어떤 선언을 넣는지, 어떤 매크로를 쓰는지)은 md에서 가져와 describe()와 Test Writer 프롬프트에 넣습니다.

10.3 md가 들어오면 하는 일

  1. md를 읽고 도구 호출 방식(CLI/라이브러리), 입력(심볼 목록? 헤더?), 출력(파일 위치, 형식), 테스트에서 스텁을 제어하는 방법을 파악한다.
  2. 백엔드별 stub_adapter.py를 구현한다.
  3. describe()가 돌려줄 요약을 md에서 뽑는다. 길면 프롬프트 예산에 맞게 줄인다.
  4. 6장 링크 범위 판정의 undefined/must_stub 심볼이 자동으로 plan_stubs에 들어가게 연결한다.
  5. 샘플 프로젝트에서 스텁 포함 e2e 테스트를 추가한다.

10.4 md가 없는 동안

NoopStubAdapter가 동작합니다. 스텁이 없으므로 undefined 심볼이 있는 함수는 narrow_scope 또는 untestable로 처리되고, 리포트에 "스텁 도구 연동 필요"로 표시됩니다. static 대상 함수는 설정 static_access = "include_source"일 때만 소스 파일 include 방식으로 접근하고, 기본값(stub_tool)에서는 "스텁 도구 연동 필요"로 표시됩니다. 순수 함수(외부 호출이 없거나 external뿐인 함수)는 완전히 동작합니다.

11.3 HTML 뷰어 (genut view)

의존성 없는 단일 HTML 파일로, 실행 하나를 다음처럼 보여 줍니다.

  • 상단 요약: 함수, 결과(통과/제거/의심), 소요 시간, 토큰, 사용한 모델, 규칙 md 버전
  • 타임라인: 8단계를 가로로. 각 단계를 펼치면 에이전트 호출(프롬프트 전문과 응답 전문, 파싱 결과), 도구 호출(빌드/실행 명령, 종료 코드, 소요 시간), 판정(왜 다음 단계로 갔는지 / 왜 수정 루프에 들어갔는지)
  • 케이스 보드: 케이스별로 상태 변화(new → fail → fix → pass)를 칸으로. 칸을 누르면 그 시점의 소스, 진단, 분류, 전략, diff
  • 진단 패널: 구조화 진단과 원본 로그를 나란히. "축약본에서 빠진 부분"도 볼 수 있게 원본에 링크
  • 크래시 패널: 크래시 브리프와 원시 oops, 심볼화 결과
  • 예산 게이지: 반복/토큰/시간이 얼마나 남았었는지

뷰어는 trace.jsonl과 디렉터리의 파일만 읽어 렌더링하므로, 기록 형식이 안정되면 뷰어는 독립적으로 개선할 수 있습니다.

11.5 여러 프로덕트 운영: 공통 정보와 프로덕트 정보의 분리

GenUT는 한 번 셋업하면 여러 프로덕트의 코드에 대해 테스트를 생성합니다. 생성하면서 쌓이는 정보는 프로덕트와 무관하게 쓰이는 것과 그 프로덕트에서만 쓰여야 하는 것이 섞이면 안 됩니다. 섞이면 A 프로덕트의 헤더 경로나 심볼 이름이 B 프로덕트 프롬프트에 들어가 오히려 성공률을 떨어뜨립니다.

두 저장 위치

범위위치담는 것
공통(global)$GENUT_HOME/ (기본 ~/.genut/)LLM provider 설정, 예산 기본값, 공통 규칙, 역할 프롬프트 튜닝본, 공통 스텁 도구 md, 프로덕트 무관 지식, 실패 패턴→수정 사례, 커널 플래그 정제 학습 목록, 모델별 성공률 기준치
프로덕트(product)$GENUT_HOME/products/<이름>/프로덕트 설정(백엔드, compile DB, 스크립트, test_file), 프로덕트 추가 규칙, 프로덕트 전용 스텁 md(있으면), 프로덕트 지식, 링크 범위·사전검증 캐시, 소스 버그 의심 목록, 실행 기록, 평가 코퍼스
$GENUT_HOME/
├── config.toml              # 공통 설정
├── products.toml            # 등록된 프로덕트 이름 → 루트 경로
├── rules/                   # common.md, gtest.md, kunit.md (공통)
├── prompts/                 # 역할 프롬프트 (사용자 튜닝본, 없으면 패키지 기본)
├── stub-tools/              # 공통 스텁 도구 md
├── knowledge/
│   ├── global.md            # 프로덕트 무관 지식
│   ├── fix_patterns.yaml    # 실패 분류+메시지 패턴 → 성공한 수정
│   └── flag_sanitizer.learned.yaml
├── evals/baselines/         # 모델별 기준 성공률
└── products/<이름>/          # 프로덕트 폴더 (아래). 소스 트리 밖에 둔다

$GENUT_HOME/products/<이름>/
├── product.toml             # 프로덕트 설정 (소스 트리 루트 경로 포함)
├── rules/                   # 프로덕트 추가 규칙
├── stub-tools/              # 프로덕트 전용 스텁 md (있으면 공통 대신 사용)
├── knowledge/
│   ├── product.md           # 프로덕트 지식
│   ├── linkscope.cache.json
│   ├── preflight.cache.json
│   ├── fix_patterns.yaml    # 프로덕트 심볼이 든 수정 사례
│   └── suspected_bugs.md
├── runs/
└── evals/corpus/

프로덕트는 genut product add <이름> --root <소스 트리 경로>로 등록합니다. 이때 $GENUT_HOME/products/<이름>/이 만들어지고 product.toml에 소스 트리 루트가 기록됩니다. genut gen은 현재 디렉터리가 등록된 소스 트리 중 어디에 속하는지로 프로덕트를 자동으로 찾습니다(--product로 지정 가능). 프로덕트 소스 트리 안에는 GenUT 파일을 두지 않으므로, 소스 저장소를 더럽히지 않고 여러 작업 트리에서 같은 프로덕트 정보를 공유합니다.

읽을 때: 겹쳐 올리기

설정, 규칙, 지식 모두 공통 → 프로덕트 순으로 겹쳐 올립니다. 같은 항목이 양쪽에 있으면 프로덕트가 이깁니다.

  • 설정: 내장 기본값 < $GENUT_HOME/config.toml < product.toml < CLI 플래그
  • 규칙: 공통 규칙 뒤에 프로덕트 규칙을 덧붙임. 프롬프트에는 "공통 규칙"과 "이 프로덕트 규칙"으로 구분해 넣음
  • 지식: 프롬프트에 global.md와 product.md를 각각 토큰 예산 안에서 넣음. 다른 프로덕트의 지식은 절대 로드하지 않음
  • 스텁 md: 프로덕트 stub-tools/가 있으면 그것, 없으면 공통
  • 소스 버그 의심 목록: 같은 함수를 다시 생성할 때 "이전에 소스 문제로 제외된 케이스"를 Test Writer·Fixer에 알려 같은 시도를 반복하지 않게 함. 대상 함수 본문 해시가 기록 당시와 다르면 무효로 보고 다시 시도

쓸 때: 범위를 정하는 규칙

쌓이는 정보는 누가 쓰느냐에 따라 범위가 정해집니다.

정보누가 쓰나범위이유
링크 범위 캐시, 사전검증 캐시코드프로덕트경로·심볼이 프로덕트 고유
소스 버그 의심 목록코드프로덕트그 소스의 사실. 함수 본문 해시와 함께 저장해 다음 생성에서 참고
커널 플래그 정제 학습 목록코드공통툴체인 특성이지 프로덕트 특성이 아님
실패 패턴 → 수정 사례코드 + Note Keeper둘 다패턴은 공통, 수정 내용에 프로덕트 심볼이 있으면 프로덕트
자유 서술 지식 노트Note Keeper 에이전트둘 다아래 검증 규칙으로 결정

Note Keeper는 실행이 끝난 뒤 실행 기록을 보고 "다음에 도움이 될 사실"을 뽑아 노트로 남기는 에이전트입니다. 노트마다 scope: global | product와 근거를 함께 냅니다. 코드가 다음 규칙으로 검증합니다.

  1. 노트에 프로덕트 루트 아래 경로, 프로덕트 분석에서 나온 심볼·타입 이름, 프로덕트 설정값이 하나라도 있으면 무조건 프로덕트로 강등한다.
  2. 공통 노트는 "어떤 프로덕트에서도 참"이어야 한다. 처음에는 공통 후보로 프로덕트 지식에 저장되고, 다른 프로덕트에서도 같은 노트가 생기면 자동으로 공통으로 승격된다(auto_promote_after_products, 기본 2). "같은 노트"는 문장 해시가 아니라 정규화 키(실패 분류 + 전략 + 프로덕트 심볼·경로를 자리표시자로 바꾼 문장)로 비교한다. 자동 승격이 되지 않아도 genut knowledge list --candidates가 분류별로 후보를 묶어 보여 주므로 사람이 genut knowledge promote <id>로 승격할 수 있다.
  3. 노트는 짧은 한 문장 + 근거 실행 ID.
    • 공통: "KUnit에서 kunit_kzalloc 결과를 구조체 포인터 필드에 넣지 않으면 null_deref가 난다 (runs: alpha/…, beta/…)"
    • 프로덕트: "drivers/foo/foo.c의 foo_init은 foo_hw_reset 스텁이 0을 반환해야 정상 경로로 간다 (run: 20261022-…)"

다음 생성에 들어가는 것과 기록으로만 남는 것

두 저장소의 내용이 모두 생성 프롬프트에 들어가는 것은 아닙니다. 생성 품질에 영향을 주는 "학습된 정보"는 지식 노트, 실패 패턴 수정 사례, 플래그 학습 목록, 소스 버그 의심 목록 네 가지이며, 범위 검증 규칙은 이 중 에이전트가 쓰는 앞의 두 가지에 적용됩니다.

항목내용
전제집합 파일 경로([kunit] test_file)가 GenUT 실행 전에 사용자에 의해 해당 디렉터리의 Makefile과 Kconfig에 등록되어 있어야 한다. 함수별 테스트 파일(test_dir)은 집합 파일이 #include하므로 따로 등록하지 않는다. GenUT는 커널 트리의 빌드 설정을 수정하지 않으며, 그 경로에 테스트 파일을 쓰기만 한다
호출<script> <test_file> --mode build|run|all [--filter <suite>.<case>] --log <path> [--coverage-out <dir>]
하는 일--mode build: 등록된 테스트 파일을 포함해 커널(또는 모듈)을 빌드만. --mode run: 마지막 빌드 결과를 QEMU에서 실행만. --mode all: 둘을 연달아. 증분 빌드+실행 1회 약 8분이며, 설정 변경 뒤 첫 빌드는 훨씬 길 수 있다
GenUT의 사용사전검증(3)은 build만. 케이스 격리 재실행(8.4)은 파일이 바뀌지 않았을 때 run만. 그 외는 all. 1회 상한은 script_timeout_sec
필터--filter는 선택(script_supports_filter). 지원하지 않으면 GenUT는 용의자 케이스만 담은 파일을 써서 all로 다시 돌린다
커버리지--coverage-out <dir>가 주어지면 실행 후 게스트의 /sys/kernel/debug/gcov 데이터를 lcov 형식 <dir>/coverage.info로 저장. CONFIG_GCOV_KERNEL과 대상 파일의 GCOV_PROFILE 설정은 사용자가 준비
종료 코드0 = 실행 완료(테스트 결과는 로그로 판단), 10 = 빌드 실패, 20 = 실행 실패(부팅 불가 등), 그 외 = 스크립트 오류
출력전체 로그는 --log 파일에. stdout은 짧은 진행 메시지만
빌드 실패 시컴파일러 출력이 로그 파일에 그대로 포함되어야 함 (진단 파서가 읽음)
